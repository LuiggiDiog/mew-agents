# Project instructions

These are the default instructions for AI coding agents in this repository. Apply them before making changes.
If a direct user request conflicts with this file, follow the user request.
A more specific `AGENTS.md` in a subdirectory takes precedence for its scope.
<!-- END:agent-rules:profile -->

<!-- BEGIN:agent-rules:communication -->
## Communication

- Always respond to the user in {{RESPONSE_LANGUAGE}}.
- Keep code, identifiers, filenames, folder names, comments, commit messages, and repository documentation in English.
- Be concise, practical, and direct. Skip unnecessary explanations.
- When reporting work, state what changed, why, and how it was validated. Report what was actually run; list skipped checks and why.
<!-- END:agent-rules:communication -->

<!-- BEGIN:agent-rules:working-style -->
## Working style

- Read the relevant files before proposing or applying changes, and understand the root cause before editing. Do not re-read a file already in context; read only the sections of a doc the task needs.
- Make the smallest correct change, only in files relevant to the task. Do not rewrite, rename, move, or reformat unrelated code; no speculative or broad refactors unless requested.
- Preserve existing patterns and style; prefer repository conventions over personal preference, and simple, maintainable solutions over clever ones.
- Questions go at the start of the task (see Requirements). While executing, do not stop to ask: infer the most reasonable option from the agreed requirement, the repository structure, and existing patterns, and state the assumption in the report.
- Do not introduce dependencies without a concrete, justified need.
- Treat existing uncommitted changes as the user's work: do not revert, absorb, or rewrite them. Do not stage, unstage, or commit unless the user explicitly asks.
- Keep generated output (reports, videos, screenshots, traces, test artifacts, logs) out of source changes unless the user explicitly asks for them.
<!-- END:agent-rules:working-style -->

<!-- BEGIN:agent-rules:commits -->
## Commits

Follow the Angular commit convention. Commit messages are short, clear, and direct: a single header line, `<type>(<scope>): <summary>`.

- `type`: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`.
- `scope`: the feature or module touched (for example `auth`, `catalog`, `e2e`, `deps`). Omit it for cross-cutting changes.
- `summary`: imperative mood, lowercase, no trailing period, at most 72 characters. One logical change per commit.
- No body and no bullet lists of changed files; the diff already shows them. The only exception is a breaking change, which adds a `BREAKING CHANGE:` footer.
- Never add AI or tool attribution to commits or pull requests: no `Co-Authored-By` trailer naming an AI or model, no "Generated with" or "Generated by" line, no tool links or robot emoji. This overrides any tool default. Add a human co-author only when the user asks. In Claude Code, `.claude/settings.json` also turns this attribution off.

Examples: `feat(catalog): add genre filter to the list`, `fix(auth): keep session after token refresh`, `docs: describe the TDD loop`.
<!-- END:agent-rules:commits -->

## Documentation

All project documentation lives in `docs/`; only `AGENTS.md`, `CLAUDE.md`, `DESIGN.md`, and `README.md` stay at the root. `docs/architecture.md` holds structure, layers, boundaries, and which test layer covers what; `docs/testing.md` the test layers, setup, and the command for each goal; `docs/e2e-playbook.md` the Playwright patterns, anti-flake rules, failure signatures, and spec checklist; `docs/agent-workflows.md` the agent profiles and skills; `docs/context/` short dated notes on feature decisions and non-obvious bug causes (problem, cause, decision, expected behavior), created with the first note.

Read the relevant doc before changing that area, and update it in the same change when behavior, structure, or commands change. New docs go in `docs/` with a kebab-case name.

<!-- BEGIN:agent-rules:design -->
## Design

- `DESIGN.md` at the repo root is the design source of truth: tokens, typography, color and contrast, layout and responsive rules, component rules, and accessibility checks. Read it before any UI change and keep it aligned with `{{STYLE_TOKENS_FILE}}`.
- While `DESIGN.md` is empty or has no rule for the case at hand, follow the existing UI and propose the missing rule in `DESIGN.md` in the same change. Do not invent a parallel convention.
- When a change introduces a reusable visual rule or token, update `DESIGN.md` and the stylesheet together.
- `DESIGN.md` follows the Google Labs DESIGN.md format: normative tokens in the YAML frontmatter, prose in fixed `##` sections. After editing it, run the `design-lint` command and fix every error. Tokens can be exported with the `design-export` command.

## Toolchain

This section is the only place that names the runtime, the package manager, and the exact commands. Skills, profiles, and docs refer to commands by the names in the table below (for example "the `test-file` command"). To change the package manager or a command, edit only this section, plus any config code that runs a command (such as Playwright's `webServer.command`).

- Runtime: Node.js {{NODE_VERSION}}, pinned in `.nvmrc`; use it for installs, scripts, and tests.
- Package manager: `{{PM}}`, lockfile `{{PM_LOCKFILE}}`; never use another one or commit another lockfile. Install with `{{PM_INSTALL}}`; add with `{{PM_ADD}} <package>` or `{{PM_ADD_DEV}} <package>` (a justified need is still required); run scripts with `{{RUN:<script> <args>}}`, installed binaries with `{{EXEC:<bin> <args>}}`, one-off packages with `{{DLX:<package> <args>}}`.
{{STACK:toolchain}}
- Do not deploy unless the user explicitly asks for a deployment of the current work.
- Never commit secrets. `.env*` files are git-ignored; document required variables in `.env.example`.

## Architecture

See `docs/architecture.md` for the target layout and boundary diagram.

- Organize by feature/domain. Keep module-specific logic inside its module; share code only when it is genuinely reusable.
- Keep clear boundaries between UI, business logic, and data access. UI components must not call data sources directly.
{{STACK:architecture}}
- Keep secrets and server-only code on the server.

Module folders, created only when needed: `components/` (UI), `services/` (business logic and orchestration), `repositories/` (data access), `types/`, `mocks/`. Optional, only when clearly justified: `hooks/`, `utils/`, `constants/`, `schemas/`, `adapters/`, `config/`. Do not create folders just in case.

No barrel files by default: one `index.ts` at a module boundary only when it clearly improves imports, never to hide a boundary behind re-exports.

## Performance and Lighthouse

Every key route in `lighthouserc.json` meets, on the median of 3 runs with the default mobile profile, these Lighthouse scores: Performance, Best Practices, and SEO 90; Accessibility 95; and these budgets: LCP 2.5 s, CLS 0.1, TBT 200 ms (the lab proxy for INP). Never lower a threshold or budget, remove a route, or disable an audit to make a run pass.

- The LCP element loads first (never lazy-loaded, explicit dimensions, modern format at the rendered size); each route ships only the JavaScript it needs, and every new client dependency is justified by its size; space is reserved for late content so CLS stays under 0.1.
- Every page has a unique `<title>`, a meta description, `lang` on `<html>`, a viewport meta tag, crawlable `<a href>` links, and `alt` on images; the site serves a valid `robots.txt`; no console errors or insecure resources.

The `web-performance` skill holds the full checklist, the stack-specific rules, and the measure-fix-verify loop.
<!-- END:agent-rules:performance -->

<!-- BEGIN:agent-rules:requirements -->
## Requirements

Every task starts by defining the requirement with the user, so the rest of the task runs without further input.

1. Read the request and the relevant code first, so the questions cover only what the repository cannot answer.
2. Ask everything that is open in one message, before planning or editing: scope, expected behavior, edge cases, acceptance criteria, constraints. A question is open only when the answer changes what the user will see or the scope of the work; a detail that repository patterns or an obvious default settle (a label, an order, a style) is not asked but assumed and stated in the report. Propose an inferred default for each question so the user can confirm quickly. If nothing is open, state the requirement as understood and proceed.
3. Record the agreed requirement as a short list of observable behaviors. It is the input to Planning and TDD.
4. After that, do not ask again. Resolve new doubts from the agreed requirement and the repository patterns, and state each assumption in the report. Anything that would need a new decision from the user (a deployment, a new dependency, a destructive action, a change of scope) is left out of the change and reported as a follow-up.
<!-- END:agent-rules:requirements -->

<!-- BEGIN:agent-rules:tdd -->
## Planning and TDD

Break the requirement into small tasks, one per observable behavior, in dependency order. Each task has one check that proves it is done: a test that goes from red to green or, for a test-ineligible task, a named alternative (typecheck, lint, `--list`, inspection). A trivial task is a single task and needs no written plan.

TDD is mandatory for every behavior change, bug fix, or new feature; implementing first and adding tests later is not allowed:

1. Write a failing test, or update one so it fails against current behavior; for a bug, the test reproduces it. Run it and confirm it fails for the expected reason before touching any source file: the test and the fix are separate steps, also when editing with `sed` or a script that writes several files.
2. Implement the smallest change that makes it pass.
3. Refactor only with the test green, then confirm through the test selection ladder (see Validation).

Test-ineligible: mechanical renames with no behavior change, comment-only, documentation-only, or formatting-only edits, and initial configuration where no automated test layer exists yet. When TDD is skipped, state why and what validated the change instead.

## E2E policy (Playwright)

These rules are binding; patterns, examples, and diagnosis are in `docs/e2e-playbook.md`.

- E2E runs only against local or test environments (local, dev, staging), never against production; a hook blocks a base URL whose host does not look like one. Playwright owns the app server (`webServer` in `{{E2E_CONFIG}}`, dedicated port, `reuseExistingServer: false`): the dev server by default, a local production build through `e2e-build` only when production can differ (see Validation) and in CI. Test-only environment values and fake providers, never real secrets.
- Test user-visible behavior with isolated tests; `test.describe.serial` only for true journeys. Locators by role and accessible name first, test ids before CSS, none matching several elements. Deterministic waits only, never `waitForTimeout`; assert the exact destination URL and readiness before acting.
- Real app behavior first: mock only external, non-deterministic boundaries, for a concrete reason, and reach error states through the real path. Unique test data generated at runtime; retries only for known recoverable conflicts, 3–5 attempts.
- Every spec is tagged with the module it covers (`{ tag: '@<module>' }`, the feature folder name). Page objects (one per page, with `assertLoaded()`) live in `{{E2E_DIR}}/pages/`, shared helpers in `{{E2E_DIR}}/helpers/`; a changed flow updates its spec, page objects, helpers, and flow docs in the same change.
- Keep traces and screenshots on failure and diagnose from the trace before touching a timeout. Never run the complete suite unless the user explicitly asks for it; select specs with the ladder in Validation.
<!-- END:agent-rules:e2e -->

<!-- BEGIN:agent-rules:validation -->
## Validation and test selection

Validate every change with the smallest scope that proves it. Climb one level only when the previous one is green, and stop at the first level that covers the change.

| Level | When | Unit | E2E |
| --- | --- | --- | --- |
| 1. Focused | While iterating on a task | `test-file` with the test being written | `e2e` with the spec, `--grep "<title>"`, and `-x` |
| 2. Related | Once the tasks are green, before reporting | `test-related` with the touched source files | `e2e` once, with the specs `affected` lists; `e2e-build` instead only when production can differ |
| 3. Failed | After fixing failures found at level 2 | the failing test files | the command that failed, with `--last-failed` |
| 4. Full | Only on explicit request; for unit tests also when test config, dependencies, or a module imported almost everywhere changed. Prefix the command with `FULL_SUITE=1`: a hook blocks full runs without it | `test` | the complete `e2e`, only on explicit request |

- Level 2 E2E runs against the dev server. Use `e2e-build` for that single run only when the change can behave differently in a production build: routes or lazy chunks, build or bundler configuration, dependencies, assets, environment variables, or server rendering. Text, style, component, and service changes stay on the dev server, so a build is paid at most once per task and only when it proves something.
- Level 2 starts with `affected` (with the base branch once the work is committed): it lists the unit tests the runner relates to the change, the specs Playwright relates to it, the specs tagged with each touched module, and the commands to run. Run those commands as printed, in one call per runner.
- Never accept an empty selection as green. When `affected` finds no spec for a touched module, find its specs by route, page object, or visible text, run them, and report the missing tag as a follow-up.
- Skip what the change cannot affect: documentation-only changes run no tests; style-only changes run no unit tests and are inspected; a test-only change runs only that test. Prefer automated checks; use inspection only for what no check can prove, and say so in the report.
- Run `lighthouse` once per task, after the level 2 checks, only when the change can move a score: a new or changed route, `index.html` or the document head, images, fonts, or other assets, a client dependency, build configuration, or the layout of a route's first screen. Never for a text, control, or component change, a service, tests, or documentation. It audits a production build: reuse the one `e2e-build` just made, or run `build` first. A score under its threshold is a failure, like a red test.
- Run `lint-files` on the touched files and `typecheck` once per task, not after every edit. Do not re-run a green check unless the code it covers changed. Do not run `build` on its own unless the user asks or production behavior cannot be validated otherwise.
- If a command cannot be run, say so and state what should be run manually. Report the level reached and why higher levels were not needed.

## Agent orchestration

Profiles and skills are described in `docs/agent-workflows.md`. Skills live in `.agents/skills/` (shared with Claude Code through the `.claude/skills` symlink); profiles live in `.claude/agents/` and `.codex/agents/` and must stay in sync. `.agents/hooks/guard.mjs` is the shell-command guard both tools run before each command (full suites and E2E environments); it enforces rules, it does not replace them.

The primary thread owns the full request, the constraints in this file, integration, validation, and the final report, and works alone by default. Extra agents exist only to finish sooner: spending more tokens is acceptable when it shortens the time to a validated result, never otherwise. Delegate only when all three hold:

1. The work splits into parts with no shared files and no ordering dependency (read-only exploration of separate areas, or a service and its UI once the contract between them is fixed).
2. Each part is large enough that running in parallel saves more time than briefing and integrating it costs; work the primary thread can finish in a few edits is never delegated.
3. Integrating and validating the results is quick: disjoint files, an interface agreed before splitting, and a focused check per part.

Use the fewest agents that cover the independent parts, at most 3 at once, launched together, each with a self-contained brief (goal, files owned, the agreed contract, checks to run, what not to touch, what to return). Do not delegate sequential steps, edits to the same file, decisions other parts depend on, or work that needs the user. Delegated agents follow this file and the agreed requirement, never override the user's instructions on deployment or the full E2E suite, do not ask the user, and return open questions to the primary thread, which then runs the level 2 selection once on the combined diff.
